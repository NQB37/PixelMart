Server · User Module — Soft-Delete & Ban Logic

2 HIGH 1 MEDIUM

The new soft-delete migration (deletedAt on User) is bolted onto the existing isActive ban flag without reconciling the two as independent states. restore() and updateStatus() each write isActive without checking the other field, so a soft-deleted account and a banned account can flip each other's state in ways no admin explicitly asked for.

What's done well (2)
  • softDelete(), restore() and permanentlyDelete() all correctly reject self-targeting and re-check the row exists / is in the right prior state (if (!user.deletedAt) throw badRequest(...)) before acting.
  • listUsers's search/role/isActive filters compose cleanly with spread-conditionals — easy to extend without an if/else ladder.
HIGH correctness ✓ verified
restore() unconditionally reactivates a user, silently lifting a ban that existed independently of the soft-delete
server/src/modules/user/user.service.ts:79

The schema has exactly one isActive boolean shared by both the ban control and the soft-delete state. softDelete() sets isActive: false alongside deletedAt, but that doesn't distinguish "deleted" from "was already banned before being deleted." restore() only checks if (!user.deletedAt) throw badRequest('User is not deleted') — it never reads what isActive was before the delete, and unconditionally writes isActive: true.

Impact Admin bans a user (isActive=false), later soft-deletes that same user (isActive stays false, deletedAt set). Clicking Restore from the Deleted filter — intending only to undo the deletion — reactivates the account and clears the ban in one step. The previously-banned user regains full access with no separate unban action ever taken.

Fix Track ban state independently of soft-delete (e.g. a separate bannedAt/flag), or have restore() only clear deletedAt and leave isActive untouched — require a distinct PATCH /status call to actually unban.

    where: { id: userId },

    select: { id: true, email: true, isActive: true, deletedAt: true },
  });
}

HIGH correctness ✓ verified
updateStatus() has no guard against being called on a soft-deleted user, producing an active-but-hidden account
server/src/modules/user/user.service.ts:45

updateStatus() loads the user and writes isActive with no check of user.deletedAt. listUsers's default view filters deletedAt: null, so a soft-deleted user stays out of the default admin list regardless of isActive — but login/refreshToken only ever check isActive, not deletedAt.

Impact PATCH /users/:id/status {isActive:true} on a soft-deleted user leaves isActive:true + deletedAt non-null: the account can log in and act normally, yet is invisible in the admin's default user list and unreachable via the intended restore-then-manage flow.

Fix Reject (400) if user.deletedAt is set — status changes should route through restore first, mirroring the pattern already used by permanentlyDelete().

MEDIUM correctness ✓ verified
listUsers treats an omitted isDeleted param the same as isDeleted=false, so the admin's "All statuses" option can never actually show every user
server/src/modules/user/user.service.ts:8

deletedAt: isDeleted ? { not: null } : null has no third branch for "don't filter on deletedAt at all." When the admin UI's "All statuses" dropdown sends no isDeleted param, axios drops the undefined field entirely, and the ternary falls to deletedAt: null — silently excluding soft-deleted accounts from a filter labeled "All".

Cross-Cutting · Seller Onboarding Approval Flow

1 HIGH 2 MEDIUM

The approval state machine is PENDING → APPROVED | REJECTED, but REJECTED was only half-wired through the stack: the backend conflict check, the seller-facing wizard, and the admin's own shop list all only reason about PENDING/APPROVED.

HIGH correctness ✓ verified
A rejected seller is permanently locked out of onboarding — frontend has no REJECTED branch, and createShop's conflict check never accounts for approval status
website/seller/src/pages/RegisterShop.tsx:44 · server/src/modules/shop/shop.service.ts:39

RegisterShop only branches on PENDING (line 44) and APPROVED (line 27, via the refresh effect); everything else — including REJECTED — falls through to return <RegisterShopForm />, a blank wizard with no rejection reason shown. Resubmitting hits createShop's if (existingShop) throw ApiError.conflict('You already have a shop'), which finds the shop by ownerId alone with no approvalStatus check.

Impact Admin rejects a shop via PATCH /shops/:id/reject. The seller logs back in, sees an empty registration form (no explanation), fills it out again, and gets a generic 409 error. There is no code path that lets a rejected seller ever create a shop again or learn why they were rejected — they are stuck indefinitely.

Fix Add a REJECTED branch in RegisterShop.tsx showing shop.rejectedReason with a way to resubmit. On the backend, either delete/soft-reset the shop row on rejection, or make createShop overwrite an existing REJECTED shop instead of unconditionally conflicting.

MEDIUM correctness ◂ plausible needs a race window
approveShop/rejectShop each re-check PENDING via a separate findUnique with no lock, so two concurrent reviews can leave the SELLER role granted from an approve that should have lost to a reject
server/src/modules/shop/shop.service.ts:138

findPendingShop() is a plain read (not part of a transaction, no row lock) called separately at the top of both approveShop and rejectShop. If both fire for the same PENDING shop close together, both pass the PENDING check before either writes: approveShop's transaction sets APPROVED and upserts the SELLER role; rejectShop's plain update then overwrites approvalStatus=REJECTED.

Impact Two admins reviewing the same queue (or one admin double-clicking) can leave a shop REJECTED in the DB while its owner has already been granted and keeps the SELLER role — a rejected applicant with seller permissions.

Fix Make the PENDING check part of the same transaction as the write (e.g. tx.shop.updateMany({ where: { id, approvalStatus: PENDING }, data: {...} }) and check the affected count), so approve and reject are mutually exclusive at the DB level.

Seller Portal · Registration & Session Refresh UX

3 MEDIUM

Approving a shop mid-request requires reissuing the seller's JWT to pick up the new SELLER role. The refactor that moved this refresh logic from useRegisterShop's onSuccess into a useEffect in RegisterShop.tsx introduced three related gaps: nothing reliably triggers the refetch that would flip the effect, the refresh chain has no error handling, and the "no shop yet" 404 is suppressed too broadly.

MEDIUM correctness ✓ verified
The token-refresh-on-approval logic was moved out of useRegisterShop's onSuccess but nothing now reliably triggers it
website/seller/src/features/shop/hooks/useRegisterShop.ts:5

The diff removes a synchronous refreshToken()/getMe()/setAuth() call that used to run right after registration succeeded. Its replacement lives in RegisterShop.tsx's useEffect, gated on shop?.approvalStatus === "APPROVED" — but that only re-evaluates when useMyShop()'s query actually refetches, and useMyShop sets refetchOnWindowFocus: false with no polling interval.

Impact A seller sits on the pending-review screen with the tab open while an admin approves their shop elsewhere. The query never refetches while the component stays mounted, so approvalStatus never flips client-side, the refresh-and-navigate effect never fires, and the seller is stuck holding a CUSTOMER-only token until they manually reload.

Fix Add a refetchInterval to useMyShop while status is PENDING (poll every 10–30s), or re-enable refetchOnWindowFocus so returning to the tab picks up the change.

MEDIUM correctness ✓ verified
The refreshToken()/getMe() chain on approval has no .catch(), and the ref is latched before it runs — a failed refresh leaves the approved seller stuck with no retry
website/seller/src/pages/RegisterShop.tsx:27

hasRefreshed.current = true is set synchronously, then authApi.refreshToken().then(...) runs with no attached .catch(). If the refresh call rejects (expired cookie, transient network error, reuse-detection tripped by a raced concurrent call), the rejection is unhandled and the effect will not retry on re-render because the ref is already latched.

Impact shop.approvalStatus is APPROVED (not PENDING), so the component falls through to render the empty RegisterShopForm to an already-approved seller who can neither resubmit (409 conflict) nor reach the dashboard — a dead end with no visible error.

Fix Add a .catch() that surfaces an error state (e.g. "couldn't refresh your session — reload the page") and only sets hasRefreshed.current = true on success, so a failed attempt can retry.

MEDIUM correctness ✓ verified
skipErrorToast on getMyShop() suppresses the toast for every error status, not just the expected 404
website/seller/src/features/shop/services/shop.service.ts:21

getMyShop() passes skipErrorToast: true to silence the expected "no shop yet" 404 — but the flag applies to the whole request regardless of response status, and RegisterShop.tsx only destructures { data, isLoading } from useMyShop(), ignoring isError.

Impact If GET /shops/me fails for a real reason (500, timeout), no toast shows and no error is read anywhere; shop is undefined and isLoading resolves false, so the component falls through past both the PENDING and APPROVED branches straight to the empty registration wizard — silently presenting "no shop yet" to a seller who actually has one.

Fix Check the status code in the client's error interceptor rather than a blanket per-request flag, or have RegisterShop.tsx read isError from useMyShop() and render a distinct error state instead of falling through to the wizard.

Tooling · ESLint Flat Config

1 MEDIUM

Both website/admin and website/seller picked up an identical, currently-broken eslint.config.js change — pnpm lint does not run in either app right now.

MEDIUM correctness ✓ verified (reproduced)
Two stacked bugs break pnpm lint entirely, in both admin and seller
website/admin/eslint.config.js:21 · website/seller/eslint.config.js:21

Two separate problems, confirmed by actually running the linter: (1) parserOptions was added as a top-level sibling of languageOptions instead of nested under languageOptions.parserOptions — flat config (ESLint 10) doesn't support a top-level parserOptions key at all. (2) Even after moving it under languageOptions, project: "./tsconfig.json" points at the solution-style root tsconfig (files: [], only references to tsconfig.app.json/tsconfig.node.json) — no source file is ever a member of that program, so every .ts/.tsx file still fails to parse.

Impact pnpm lint fails immediately with "A config object is using the 'parserOptions' key, which is not supported in flat config system." CLAUDE.md requires running the linter before declaring work done — that evidently didn't happen for either app in this change.

Fix Move parserOptions under languageOptions, and point project at tsconfig.app.json (or switch to projectService: true, which auto-resolves the right tsconfig per file and needs no project path at all).
