01 helmet installed but never applied High Security
server/src/app.ts

helmet is listed in package.json dependencies but is never imported or mounted. No security headers — CSP, X-Frame-Options, HSTS, X-Content-Type-Options — are set on any response.

Fix

import helmet from "helmet";
app.use(helmet()); // before CORS middleware
02 Logout never invalidates the DB refresh token High Security / Bug
server/src/utils/cookies.ts:10  +  auth.controller.ts:28

The refresh token cookie is set with path: "/api/v1/auth/refresh". Browsers only send a cookie when the request URL starts with the cookie's path. POST /api/v1/auth/logout does not satisfy that condition, so the browser never sends refreshToken to the logout endpoint.

The if (refreshToken) guard in the controller always evaluates to false — the DB token is never deleted. The old refresh token stays valid until natural expiry. This is a silent bug; logout appears to succeed but provides no revocation.

Fix — broaden cookie path to cover both endpoints

path: "/api/v1/auth"
03 Zod transforms discarded in validate middleware High Bug
server/src/middlewares/validate.middleware.ts:8 
// result is thrown away — transforms never applied to req.body
await schema.parseAsync(req.body);
next();

The registerSchema and loginSchema both apply .toLowerCase().trim() to the email field via Zod transforms. Because the parsed result is discarded, req.body.email reaches the service as the original raw string. Users can register Test@Example.com and test@example.com as separate accounts, bypassing the @unique database constraint.

Fix

req.body = await schema.parseAsync(req.body);
04 No rate limiting on auth endpoints High Security
server/src/modules/auth/auth.routes.ts

POST /auth/login, POST /auth/register, and POST /auth/refresh have no rate limiting. The login endpoint is directly brute-forceable against any known email address.

Fix — add express-rate-limit to auth routes

import rateLimit from "express-rate-limit";
const authLimiter = rateLimit({ windowMs: 15 * 60 * 1000, max: 20 });
router.post("/login", authLimiter, ...);
05 CORS silently passes undefined origins High Security
server/src/config/cors.ts 
origin: [env.clientWebUrl!, env.sellerWebUrl!, env.adminWebUrl!]

All three env vars are typed string | undefined. The ! non-null assertions lie to TypeScript — if the variables are unset, undefined lands in the origins array. The cors package may treat undefined entries as "allow all origins," opening the server to cross-origin requests from any domain.

Fix

[env.clientWebUrl, env.sellerWebUrl, env.adminWebUrl].filter(Boolean) as string[]

06 DB token expiry hardcoded to 7 days — config says 14 Medium Bug
server/src/modules/auth/auth.service.ts:141 
// hardcoded — JWT is signed for 14d, cookie also uses 14d
expiresAt: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000),

The JWT is signed for refreshTokenExpiresIn (default "14d") and the cookie uses refreshTokenExpiresInDays (default 14), but the DB record expires at day 7. Token rotation reuse-detection rejects tokens between days 7–14 even though the JWT itself is still valid, creating inconsistent behavior.

Fix

expiresAt: new Date(Date.now() + env.refreshTokenExpiresInDays * 24 * 60 * 60 * 1000),
07 JWT secrets not validated at startup Medium Bug
server/src/config/env.ts  +  utils/jwt.ts:12,18

jwtAccessSecret and jwtRefreshSecret are typed string | undefined but used with ! assertions in jwt.ts. If these env vars are missing, the server starts successfully and crashes with an opaque runtime error only on the first token operation.

Fix — validate required env vars before app.listen()

if (!env.jwtAccessSecret || !env.jwtRefreshSecret) {
  throw new Error("Missing required JWT environment variables");
}
08 refreshTokenExpiresInDays parsing is fragile Medium Bug
server/src/config/env.ts:17 
parseInt(process.env.REFRESH_TOKEN_EXPIRES_IN || "14d", 10) || 14

parseInt("14d", 10) returns 14 only by coincidence. parseInt("2w", 10) silently returns 2 instead of 14. Any operator setting REFRESH_TOKEN_EXPIRES_IN=2w gets a 2-day expiry window — and the mismatch between the JWT expiry and cookie maxAge creates a window where one is valid and the other is not.

Fix — enforce plain integer days and validate at startup

refreshTokenExpiresInDays: Number(process.env.REFRESH_TOKEN_EXPIRES_IN_DAYS ?? 14)

11 Double-toasting on API errors Low Bug / UX
website/client/features/auth/hooks/useLogin.ts:18  +  useRegister.ts:18  +  useLogout.ts:17

The Axios response interceptor in lib/api.ts already calls toast.error() for all non-401 errors before rejecting the promise. The onError callbacks in each mutation hook call toast.error() again for the same error, showing two toasts for every API failure.

Fix — remove toast.error() from the onError handlers in the hooks; let the interceptor own it
