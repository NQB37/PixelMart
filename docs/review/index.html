Server · Auth & Token Lifecycle

5 MEDIUM 3 LOW 2 INFO

The auth subsystem is well-structured and gets the fundamentals right: bcrypt cost 12, separated JWT secrets validated at boot, HttpOnly/Secure/SameSite path-scoped refresh cookie, server-side logout revocation, and refresh-token rotation with real reuse detection. The most serious gap is that the refresh endpoint never re-checks isActive and no code revokes refresh tokens on ban, so a banned account can keep minting access tokens for the full 14-day refresh window — the ban control is effectively bypassable. Secondary issues cluster around user enumeration (distinct 'banned' message before password check, non-constant-time login, and the register conflict message) and a rate limiter that cannot see the real client IP in production because trust proxy is unset, collapsing login brute-force protection into a single shared/lockout-prone bucket. Refresh tokens are also stored in plaintext, turning a DB read into direct session takeover. Note that isAuth/requireRole are defined and tested but not yet wired to any protected route, so RBAC enforcement is not exercised in the app today.

What's done well (8)
  • Refresh-token rotation includes genuine reuse detection: a validly-signed refresh token that is not present in the DB (i.e. an already-rotated/replayed token) triggers deletion of ALL of that user's refresh tokens and a 401 (auth.service.ts lines 121-131). This is the correct rotation+reuse pattern.
  • Logout actually revokes server-side: authService.logout deletes the DB refresh token by value (auth.service.ts lines 108-112) and the controller clears the cookie (auth.controller.ts lines 27-36), so logout is not merely client-side.
  • Password hashing uses bcrypt with cost factor 12 (password.ts line 3) and comparison via bcrypt.compare — appropriate and constant-time per-hash.
  • Refresh cookie is hardened: HttpOnly, Secure in production, SameSite=Lax, path-scoped to /api/v1/auth, with an explicit maxAge (cookies.ts lines 5-11).
  • Access and refresh tokens are signed with separate secrets (jwt.ts lines 13-23), and the app fails fast at boot if either JWT secret is missing (env.ts lines 5-7).
  • Security middleware is mounted app-wide: helmet, credentialed CORS with an explicit origin allowlist, cookie-parser, and a JSON body-size limit (app.ts lines 15-20).
  • Login returns a generic 'Invalid credentials' for both unknown email and wrong password (auth.service.ts lines 75, 86), which is the right instinct (undermined only by the separate banned-message/timing leaks noted in findings).
  • requireRole is fail-closed: it defaults roles to [] when req.user is absent and denies by default (role.middleware.ts lines 7-12), and it is unit-tested (middlewares/tests/role.middleware.test.ts).
